# 08.4 当前设计问题的逐项解决记录

更新：2026-09-27。本轮解决“现在必须决定的设计问题”，实施和业务批准留在正确阶段，不混同为设计阻塞。

## 1. G-01：模型和数据路线——设计已落定

结果见[模型与数据实施方案](../04-ai-rules/02-model-data-plan.md)。

- ML-BASE-02选择D-FINE-N四类微调+PP-OCRv4 CPU，固定上游提交、初始化来源、数据/类别双向映射/微调/导出路线，不能拿COCO类别权重冒充项目模型。
- adapter明确640、RGB/0–1、PIL直接resize、orig_target_sizes=[W,H]、labels/boxes/scores、qmax/无NMS；全请求100结果上限与原图裁剪规则保持，源实现/参考语义/测试同步。
- 依据ADR-PY-01，业务、独立AI/训练统一Python3.11，通过独立依赖环境与既有HTTP边界隔离；顶层版本基线已选择，实际lock和硬件证明由I-ML-01生成。
- CUDA FP32为建议生产profile，CPU功能仍保留；两者独立bundle/lock/报告。OCR不暗换模型或GPU化。先用同协议fixture和初始化checkpoint开发，production拒绝mock/未校准/未批准bundle。
- 清单新增来源提交和runtime；16字段内容摘要绑定代码/环境，/version回显实际设备/适配器。生成器与门禁不再仅接受旧模型，新负例覆盖错设备、精度和报告复用。
- 数据不足和目标不达标有继续采集/微调与ADR替换路径，不让开发者自行猜模型、输出字段或错误行为。

当前不应要求：已经训练好的权重、真实hash、实测显存和识别报告。它们分别属于I-ML-01至04和R-ML-01，不阻止设计完成。

## 2. G-02：验收与规则——设计已落定，业务批准待执行

结果见[分层验收策略](../07-quality-operations/04-acceptance-policy.md)和[开发目标policy](../../contracts/development-acceptance-policy.json)。

- E工程要求现在冻结：权限、状态、幂等、旧结果围栏、证据完整等必须通过。
- M模型开发有明确数值目标、逐类/逐规则公式、样本下限、P95负载和不足样本inconclusive处理，不再只有“将来由专家确定”的空白。
- 这些数值明确标proposed，是开发目标而非已证明的安全标准。P正式试点必须在test解封前由真实责任人批准policy和规则，禁止看成绩后调低目标。
- 校准候选网格、比较运算、选择顺序、并列规则、失败处理已明确；仅用validation，缺乏可行解就failed。
- 真实化学兼容规则仍需来源和专家工作包，不编造内容；没有专家批准时开发继续、生产发布关闭。
- 清单、评测、policy和服务端只读批准台账使用明确hash绑定，模拟场景不能仅靠evaluation_passed=true进入production。

当前不应要求：真实数据已采集、专家已经签字、指标已经达标。这些是实施/发布工作，不能冒充本轮完成。

## 5. 当前可交付结论

Implementation Readiness Review的六项新增编码前问题已经形成[逐项关闭记录](06-implementation-readiness.md)。这些是对跨模块实现细节的补齐，不以本文件此前G项关闭声明代替复查；机器证据、独立批准、真实部署验收各自单列。

本次列出的G-01/G-02/G-03在“设计要做哪些决定”层面已分别解决；开发者可以按明确任务开始实现，不再等待不存在的运行结果。实施可用性、真实安全有效性和人工批准仍未完成。

后续若技术原型证伪版本/性能假设，走ADR和回归，不重新把所有文档无限期标记未完成。本轮不执行业务开发、模型训练、数据库启动或Git远程动作。
