# Gate 3 测试验收、部署与监控设计

状态：Gate 3 方案已确认，待用户确认关闭 Gate 3

本文件基于 Gate 0～2 已确认设计，定义编码前的质量门禁、环境、发布、监控、备份恢复和运行手册。它不创建业务代码、数据库迁移、依赖锁文件或部署脚本。

## 1. Gate 3 目标与退出条件

Gate 3 的目标是让后续编码任务拥有可执行的验证和运行标准，而不是追求一次性覆盖所有未来能力。

退出条件：

1. 每个 P0/P1 需求映射到至少一个自动化或人工验收用例。
2. 领域状态机、权限、租户隔离、审计和幂等具有拒绝路径测试。
3. AI 和规则有冻结数据集、指标口径、版本记录和失败回退。
4. 断公网环境可完成真实试点主流程。
5. 发布、回滚、备份恢复和死信重放均有演练步骤。
6. CI 检查、环境配置、密钥注入和制品版本可追踪。
7. 监控指标有阈值、告警等级、责任人和关闭条件。

## 2. 测试金字塔

### 2.1 单元测试

覆盖：

- Finding 和 RemediationTask 状态转移；
- 角色、租户和实验室授权判断；
- 风险评分因子；
- 规则 DSL Schema、优先级和冲突检测；
- 化学品别名标准化；
- 幂等键、分页和过滤校验；
- Outbox 领取、重试和死信状态。

要求：拒绝路径和边界路径必须与正常路径同等重要；不以覆盖率单一数字代替业务断言。

### 2.2 集成测试

使用隔离 MySQL、Redis 和 MinIO 测试实例，覆盖：

- 业务事务与 Outbox 同事务提交；
- 上传元数据与对象存储校验；
- Celery Worker 从 Outbox 到推理结果回写；
- 规则版本读取和历史版本绑定；
- 通知创建和已读状态；
- CSV/PDF 导出及短期下载链接。

### 2.3 契约测试

- API 与前端共享 OpenAPI Schema；
- 业务 API 与 AI HTTP/JSON v1 契约；
- Celery 任务消息 Schema；
- MinIO 对象键、租户前缀和元数据约定；
- 外部通知适配器接口，即使首期没有外部实现也必须验证空实现。

### 2.4 E2E 测试

主链：

```text
登录 -> 选择实验室 -> 按模板上传 -> 质量检查
-> AI处理 -> 人工复核 -> 待派发
-> 分派整改 -> 上传证据 -> 复查 -> 销项 -> 导出报告
```

必须覆盖：质量失败补拍、OCR人工录入、无法判断、Finding驳回、整改逾期、复查驳回、死信重放和断公网运行。

## 4. AI 和规则评测

### 4.1 数据集

- 基线集在第 1～3 天冻结；候选验收集在第 8～10 天冻结。
- 每类目标至少记录 20 个正样本和 20 个负样本作为基线目标；候选集目标为每类 50 个独立样本，样本不足必须如实报告。
- 同一实验室、采集批次和场景不得跨训练、验证和测试集合。
- 真实现场数据与历史回放数据分别报告；合成增强只用于训练增强。

### 4.2 指标

- 目标检测：mAP、召回率、误检率；
- OCR：字符准确率、字段准确率、人工修正率；
- 标准化：Top-1/候选覆盖率、人工确认率；
- 规则：高风险问题召回率、误报率、无法判断率；
- 工程：P50/P95/P99 推理耗时、失败率、队列积压；
- 业务：巡检耗时、AI采纳率、整改按期率、复查驳回率。

### 4.3 版本与回归

评测报告必须绑定数据集版本、模型版本、规则版本、阈值、代码提交和运行环境。新模型或规则必须先通过冻结回归集，再进入试点；指标下降时回滚，不修改历史结果。

## 5. 性能、可靠性和安全测试

### 5.1 性能

- 推荐配置/GPU：完整推理 P95 ≤30 秒；
- 最低配置/CPU：允许超过 30 秒，但必须异步完成或给出稳定失败状态；
- 上传、质量检查、列表查询和复核接口分别压测；
- 测试单 Worker、并发 Worker、队列积压和对象存储容量增长。

### 5.2 故障注入

- AI 服务超时、5xx、进程重启；
- Redis 暂时不可用；
- MySQL 连接池耗尽；
- MinIO 上传中断；
- Worker 在任务执行中退出；
- 网络恢复后死信重放。

### 5.3 安全和隐私

- 跨租户、跨实验室、对象键路径穿越和批量接口越权；
- Cookie、会话撤销、登录限流和密码策略；
- JPEG/PNG/WEBP、伪造 MIME、超大像素和 EXIF 清理；
- 原图导出额外授权、短期 URL 和审计；
- 敏感文件、密钥、`.env`、真实图片和 `.obsidian/` 扫描。

## 6. 环境拓扑

```text
开发 dev：本地容器/进程，模拟数据
    |
staging：接近试点配置，脱敏数据，自动测试
    |
pilot：校内局域网，真实授权数据，正式权限和备份
    |
demo：本地预置模型/规则/数据，断公网可运行
```

环境原则：

- Demo 数据不得进入 pilot；
- 真实图片不得进入 dev；
- 配置通过环境变量或密钥文件注入，不提交真实密钥；
- 模型、规则、迁移和应用版本必须在发布记录中绑定；
- 断公网时不依赖云 OCR、LLM、CDN、在线字体或外部 DNS。

## 7. CI/CD 和发布

### 7.1 CI 检查

CI 平台确认使用 GitHub Actions。每个 Pull Request 至少执行：

1. 格式化和静态检查；
2. Python/TypeScript 类型检查；
3. 单元测试；
4. API/AI/任务契约测试；
5. 迁移可创建和回滚检查；
6. OpenAPI Schema 校验；
7. 敏感文件和依赖许可证扫描；
8. 构建 Web、API、Worker 和 AI 制品。

工作流文件在编码阶段落地为仓库内的 .github/workflows/ 配置；本 Gate 只冻结检查范围，不提前创建工作流文件。

### 7.2 制品仓库与保留

- 默认使用 GitHub Container Registry（GHCR）存储 Web、API、Worker 和 AI 镜像。
- 学校网络或合规策略不允许访问 GHCR 时，使用校内 Harbor；完全离线时导出经过校验的离线镜像包并通过校内介质导入。
- 镜像必须以不可变版本标签（Git 提交 SHA/发布版本）发布，禁止以 latest 作为生产部署引用。
- 默认保留最近 10 个稳定版本和最近 30 天的构建版本；校方存储政策不允许时由租户运维配置覆盖，并记录变更审计。

### 7.3 发布顺序

```text
备份 -> 迁移预演 -> 发布兼容应用
-> 执行 expand 迁移 -> 健康检查
-> 启用 Worker/AI -> 回归检查 -> 试点放量
```

### 7.4 回滚

- 应用回滚到上一稳定镜像；
- 模型回滚到上一模型版本；
- 规则回滚到上一规则版本；
- 数据库优先执行补偿迁移，不直接删除已写入数据；
- 回滚原因、操作者、版本和影响范围写入审计。

## 8. 备份、恢复和灾备

- MySQL 每日全量备份，必要时增加 binlog/增量备份；
- MinIO 图片和报告独立备份；
- 备份目标为校内独立 NAS 或备份服务器，不与应用主机共用故障域；
- 备份传输使用 TLS，备份文件使用 AES-256 加密，密钥通过校内密钥管理或受控密钥文件注入；
- 默认备份窗口为 Asia/Shanghai 每日 02:00～03:00。窗口可按校方维护安排调整，但必须记录配置和审计；
- 备份加密、限制访问并遵守租户留存策略；
- 每月至少一次恢复演练；
- RPO 目标 ≤24 小时，RTO 目标 ≤4 小时；
- 恢复后校验数据库、对象存储、Outbox 和模型/规则登记的一致性。

## 9. 监控和告警

### 9.1 指标

| 类别 | 指标 |
|---|---|
| API | 请求量、错误率、P95/P99、4xx/5xx |
| 队列 | 深度、最老任务年龄、重试数、死信数 |
| AI | 单阶段耗时、完整耗时、低置信度率、失败率 |
| 业务 | Finding确认率、驳回率、无法判断率、整改按期率 |
| 资源 | CPU、内存、磁盘、GPU显存、MinIO容量、MySQL连接 |
| 安全 | 登录失败、越权拒绝、原图导出、删除和规则发布 |

### 9.2 告警等级

- P1：数据不可访问、批量任务失败、备份失败、跨租户异常；立即处理。
- P2：推理 P95 持续超标、队列积压、磁盘接近阈值、死信增长；工作日内处理。
- P3：单用户上传失败、报表延迟、低置信度率波动；纳入日常复盘。

每条告警必须定义阈值、持续时间、责任人、处理动作和关闭条件；首期通知通过站内通知，运维可按环境配置其他渠道。

试点值班基线为工作日 09:00～18:00（Asia/Shanghai）：P1 告警 30 分钟内响应，P2 告警 4 小时内处理，P3 告警 1 个工作日内纳入处理。非值班时段的 P1 由站内通知记录并在下一个值班时段升级确认；若校方另有值班制度，以经审批的环境配置为准。

## 10. 运行手册和断公网验收

### 10.1 日常检查

- 检查 API、Worker、AI、MySQL、Redis、MinIO 健康状态；
- 检查队列最老任务和死信；
- 检查磁盘、对象存储和备份结果；
- 检查模型/规则当前版本；
- 检查审计写入是否正常。

### 10.2 断公网验收步骤

1. 预置账号、模型、规则、前端静态资源和 Demo 数据；
2. 断开公网但保留校内局域网；
3. 登录并选择实验室；
4. 上传新图片并完成质量检查；
5. 完成 AI 处理、人工确认、整改、复查和销项；
6. 导出 CSV/PDF；
7. 检查日志中不存在外部网络依赖；
8. 恢复网络后确认没有产生重复任务或重复通知。

## 11. Gate 3 待确认项

以下事项已由项目方确认，作为 Gate 3 基线：

1. CI 使用 GitHub Actions；具体检查命令在编码阶段随工作流文件落地。
2. 默认镜像仓库为 GHCR；学校受限时切换 Harbor 或离线镜像包；镜像使用不可变版本标签并按保留策略清理。
3. 备份存储在校内独立 NAS/备份服务器；传输使用 TLS，文件使用 AES-256 加密；每月组织恢复演练。
4. 试点值班时间为工作日 09:00～18:00（Asia/Shanghai）；P1 30 分钟内响应、P2 4 小时内处理、P3 1 个工作日内处理。
5. MySQL/MinIO 默认每日 02:00～03:00（Asia/Shanghai）备份，按校方维护安排可调整并审计。

具体责任人姓名、校方备份保留年限和最终维护窗口仍属于部署前环境配置，不阻塞 Gate 3 设计关闭。
