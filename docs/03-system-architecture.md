# 03 系统架构与技术方案

状态：**待用户确认**

## 1. 总体架构

```text
响应式 Web（手机采集 / 管理后台）
              |
        API 与认证层
              |
业务服务：实验室、巡检、复核、整改、报表、审计
              |
异步任务层：队列、状态、重试、超时
       /                 \
AI 推理服务              规则与决策服务
质量/检测/OCR/实体       相容性/严重度/解释
              |
MySQL + MinIO + Redis + 模型/规则登记
```

## 2. 服务边界

### Web应用

负责登录、实验室/模板管理、拍摄上传、任务状态、复核、整改、报表和权限展示，不在浏览器中实现安全规则。

### API/业务服务

负责权限、领域状态机、数据校验、任务编排、审计和导出。

### AI服务

只输出结构化事实：图像质量、目标框、OCR 字段、置信度、候选实体。不得直接写入“已确认风险”。

### 规则服务

读取标准化化学品、位置关系和规则版本，输出触发规则、严重度建议、解释和是否需要人工确认。

### 异步任务服务

队列任务类型包括 `image_quality`、`detection`、`ocr`、`entity_normalization`、`compatibility_check`、`report_export`。每个任务具备幂等键、重试次数、超时和失败原因。

## 3. 推荐实现原则

- 首期采用模块化单体 + 独立推理进程，避免过早拆分微服务。
- FastAPI 作为 API/AI 服务候选；MySQL 保存业务和 JSON 证据；MinIO 保存图片和报告；Redis 保存队列/缓存/短期状态。
- 所有外部依赖通过接口隔离，便于替换 OCR、检测模型、对象存储和通知适配器。
- 领域状态变化使用事务和审计事件，避免前端直接修改状态。

## 4. 处理时序

1. 客户端申请上传凭证并提交采集元数据。
2. API 校验用户、实验室和模板权限，创建巡检项。
3. 图片写入对象存储，创建异步推理任务。
4. 质量检查失败则状态为 `needs_retake`，不进入后续模型。
5. 质量通过后依次执行检测、OCR、标准化和规则检查。
6. 结果写入不可覆盖的推理版本记录，业务层创建待复核问题。
7. 安全员复核后，管理者派发整改任务。

## 5. 可观测性

必须记录请求 ID、巡检项 ID、任务 ID、模型/规则版本、耗时、重试次数、失败原因和资源占用。核心指标包括 API 成功率、队列长度、单图耗时、低置信度率、人工驳回率、类别误报率、任务长期处理中数量。
